# Тесты ParTuT

Локальные тесты **без сети и без боевой базы** (временный SQLite + заглушки Telegram).

## Как запускать

**Перед каждым деплоем** прогони:

```bash
python tests/run_all.py
```

- Код выхода `0` — всё зелёное, можно пушить на Render.
- Код выхода `1` — есть падения, **не деплой**, сначала почини.

**Перед релизом** прогони ещё дважды — на другой базе и в другом часовом поясе.
Оба прогона ловят то, чего обычный набор не видит в принципе:

```bash
TEST_DATABASE_URL=postgresql://... python tests/run_all.py    # магазин работает на Postgres

Внутри run_all.py — pytest, поэтому доступно и всё его:
    venv/bin/pytest tests/ --lf         только упавшие в прошлый раз
    venv/bin/pytest tests/ -k заказ     по имени
    venv/bin/pytest tests/test_till.py  один файл

Двух запускателей нет намеренно. Были — и разошлись: run_model_reviews
существовала, а в списке её не было, и она не гонялась ни разу.
TZ=UTC python tests/run_all.py                                # Render живёт по UTC
```

Диалекты баз расходятся (регистр в LIKE, строгий GROUP BY, ON CONFLICT вместо
INSERT OR IGNORE), а разница поясов однажды уже стоила магазину трёх часов:
заказ, сделанный в час ночи, записывался вчерашним.

Линтер (ищет неиспользуемые импорты, мёртвый код, обращения к несуществующим
именам) — отдельно, локально так:

```bash
pip install ruff && ruff check .
```

Эти же четыре сочетания идут сами при каждом пуше — см. `.github/workflows/tests.yml`.
Проверка, которую запускает человек, однажды не запускается.

Отдельный файл можно запускать сам по себе:

```bash
python tests/test_order_lifecycle.py
python tests/test_messaging.py
```

## Учения по восстановлению

Копия, которую ни разу не разворачивали, — это надежда, а не гарантия. Раз в
несколько месяцев стоит проверять её по-настоящему: не «файл скачался», а
«магазин на нём поднялся».

Проверено 19 августа 2026: копия из бота залита в отдельную пустую базу, все 24
таблицы совпали по числу строк, товары, заказы, реквизиты и доступы — по
содержимому, магазин на этой базе отвечает.

**И этого оказалось мало.** Учения проверяли только чтение — «магазин отвечает».
Записи в них не было, а сломано было именно она: копия привозит строки, но не
счётчики id, и на Postgres первый же новый заказ падал с `duplicate key` —
номер №1 в базе уже есть. Восстановление при этом выглядело безупречно.
Поэтому в порядке ниже появился шаг 5: **оформить заказ**. Учения, где ничего
не записывают, проходят и на мёртвом магазине.

Повторено 20 августа 2026, уже целиком: копия развёрнута в пустую базу
`tools/restore.py`, магазин поднят на ней, заказ оформлен по HTTP как из
приложения — получил номер 249 сразу за восстановленным 248, разрывов в
нумерации нет.

Порядок (на своей машине, боевую базу не трогаем):

```bash
# 1. Взять свежую копию из личных сообщений бота (или снять командой /backup)
# 2. Завести ПУСТУЮ базу рядом
createdb drill

# 3. Развернуть копию в неё — сначала без --yes, чтобы посмотреть содержимое
DATABASE_URL=postgresql://…/drill python tools/restore.py ~/Downloads/partut-….json.gz
DATABASE_URL=postgresql://…/drill python tools/restore.py ~/Downloads/partut-….json.gz --yes

# 4. Поднять магазин на восстановленной базе и открыть его
DATABASE_URL=postgresql://…/drill PORT=5002 python server.py

# 5. ОФОРМИТЬ ЗАКАЗ. Не «посмотреть витрину» — именно оформить, до конца.
#    Заодно завести товар в админке. Это единственный шаг, который проверяет,
#    что магазин умеет ПИСАТЬ, а не только показывать восстановленное.

# 6. Убрать за собой
dropdb drill
```

Автоматически при каждом прогоне проверяется то же самое, но на SQLite:
`run_empty_restore` в test_backup.py заливает копию в пустую базу и убеждается,
что магазин на ней работает. На Postgres второй пустой базы под рукой нет,
поэтому там — руками, по порядку выше.

Отдельно и на обоих диалектах: `run_restore_keeps_numbering` восстанавливает
копию в базу со сброшенными счётчиками — ровно то состояние, в котором они
оказываются в новой базе, — и оформляет новый заказ. Отключи в `import_tables`
строку `advance_sequences(cur)`, и на Postgres она краснеет.

## Что покрыто

- **test_order_lifecycle.py** — статусы заказа (нельзя подтвердить/выдать неоплаченный),
  идемпотентность (повтор → 409), кэшбэк один раз, возврат склада и монет при отмене,
  отмена клиентом (свой/чужой/подтверждённый).
- **test_messaging.py** — вопрос с привязкой к заказу, кликабельные контакты в обе
  стороны, тег заказа не палит чужие, HTML-экранирование текста, антиспам-кулдаун.

Новую логику — покрывай тестом здесь же, чтобы регрессии ловились до деплоя.
